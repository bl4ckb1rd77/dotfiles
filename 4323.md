Hier ist die korrigierte, präzisierte Version deines Runbooks:

---

## OpenSearch Reindexing Runbook

### 1. Vorbereitung (Infrastruktur & Cluster-State)

* **Helm-Values:** Der dedizierte `data-reindexing`-Pool ist mit den entsprechenden Node-Attributen (`node.attr.box_type: reindexing`) in den Konfigurationen hinterlegt.
* **Excludes setzen:** Alle bestehenden Nicht-System-Indizes (z. B. `bdp-*`) einmalig per API mit dem Exclude versehen, damit sie sich später nicht auf den neuen Migrations-Nodes breitmachen:
```http
PUT /bdp-*/_settings
{
  "index.routing.allocation.exclude.box_type": "reindexing"
}

```



---

### 2. Setup & Skalierung

* **Initialer Zustand:** Der Reindexing-Pool läuft im Normalbetrieb auf `0` Replicas/Pods.
* **Run-Scaling:** Vor dem Start der Migration den Reindexing-Pool auf `3` Pods hochskalieren.

---

### 3. Migrations-Prozess

1. **Sauberkeit prüfen:** Per `GET /_cat/shards?v` verifizieren, dass keine produktiven oder System-Shards mehr auf den neuen Reindex-Nodes liegen.
2. **Reindexing starten:** Das eigentliche Reindexing anstoßen. Dabei wird der temporäre Ziel-Index (mit `number_of_shards: 3`, `number_of_replicas: 0`, `refresh_interval: "-1"` und `require.box_type: reindexing`) automatisch frisch erstellt und landet dank der Shard-Anzahl sauber auf den 3 Nodes.
3. **Warten auf Durchlauf:** Dank deaktiviertem Refresh-Intervall läuft der Import mit maximaler Performance durch.

---

### 4. Prozess-Abschluss & Cleanup

1. **Index scharfschalten:**
```http
PUT /<temp-index-name>/_settings
{
  "index.refresh_interval": "1s"
}

```


2. **Temp-Indizes bereinigen:** Die temporären Migrations-Indizes löschen.
3. **Pool herunterfahren:** Den Reindexing-Pool wieder auf `0` Pods scalieren.
